# Devpost submission draft - Jus 9 DAJ

This draft is ready for editorial review but not for submission while eligibility and the other blockers in `BUILD_WEEK_STATUS_2026.json` remain unresolved.

## Project name

Jus 9 DAJ

## Tagline

Governed AI legal intake, analysis, human routing, and official case metadata without invented results.

## Track

Work and Productivity

## Inspiration

Legal teams frequently move between intake forms, documents, AI chats, process searches, and internal handoffs without one reliable shared record. The result is repeated work, weak traceability, and a dangerous blur between verified facts and generated suggestions.

Jus 9 DAJ was built around a different premise: AI should participate in the workflow without becoming the source of truth. The case record, official connectors, human roles, and audit trail remain distinct and reviewable.

## What it does

The Build Week demonstration follows one case path:

1. A team member records a fictional initial legal intake.
2. The governed backend creates or updates an official DAJ record.
3. The user sends that DAJ to a new, isolated Charlie Echo room.
4. Charlie receives a minimized case context and returns a faithful summary, missing information, supported risks, objective questions, explicit limits, and feedback.
5. The DAJ is routed to the appropriate human role for the next review.
6. A CNJ case number can be checked through a read-only DataJud connector for official public metadata.
7. One DAJ can be linked to one case, while a person can have several DAJs.
8. If an official source or authorized connector is unavailable, the workflow fails closed instead of generating a substitute result.

## How we built it

The working system combines:

- a static, responsive legal-work portal served through Cloudflare;
- a Worker gateway for authentication, permissions, policies, readiness, and audit controls;
- a Charlie Echo API for intent routing, governed context, OpenAI calls, and response contracts;
- backend-persisted DAJ records with idempotency and HMAC-SHA-256 party indexing;
- isolated per-user memory and governed Google Drive operations;
- a read-only DataJud client with tribunal aliases, validation, cache, DTO normalization, readiness, and metadata-only auditing;
- one-DAJ-to-one-case linkage; and
- automated regression, authentication, RLS, governance, response-contract, and end-to-end homologation tests.

The production Worker serves compiled assets from `dist`. Source verification is intentionally simple: the root repository has no invented package setup, and the full local audit runs with `node scripts/run-local-ci.mjs` when the related repositories are placed under the same parent folder.

## Challenges

The hardest problem was not producing legal-looking text. It was preventing a model from answering the wrong question with a polished but unrelated response. We separated operational intents from generative legal work, created response contracts for DAJ analysis and process search, and made unavailable official-source operations fail closed.

Another challenge was preserving evidence for a pre-existing product. We established a baseline commit, recorded the event time boundary in both Pacific and Brazilian time, kept related repositories explicit, and distinguished verified Codex use, verified OpenAI API source integration, and unverified runtime-model claims.

## Accomplishments

- A fictional intake can become a backend-persisted, auditable DAJ.
- DAJ analysis opens in a new room with minimized context, feedback, limits, and human routing.
- Process metadata by CNJ number uses an official read-only connector.
- Name and CPF searches never receive invented process results.
- DAJ and process linkage enforces a clear cardinality rule.
- Memory is isolated by user and temporary memory is not silently promoted.
- The local audit spans the portal, Worker, Charlie Echo API, backend exposure policies, governance structure, RLS, installation pages, and public assets.

## What we learned

Governance becomes useful only when it changes runtime behavior. A principles document alone does not stop a wrong answer; intent boundaries, data minimization, official-source status, permissions, response schemas, and tests do.

We also learned that honest limitations improve the product. Naming what DataJud does not provide, refusing generative party-search results, and separating technical integration from third-party authorization made the demonstration more credible and easier to audit.

## Third-party and safety disclosure

The project uses or evaluates OpenAI, Cloudflare, Google APIs, CNJ DataJud, GitHub, and open-source libraries. Technical availability is not treated as proof of authorization.

DataJud remains read-only and limited to public metadata by CNJ case number. No real case data, party search, case-file document, filing, service acknowledgment, or transactional court act belongs in the public demonstration. Google Drive operations require governed authorization and synthetic files. Secrets and judge credentials must never be committed or published.
